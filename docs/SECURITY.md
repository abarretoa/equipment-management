# Security

This document lists the security controls that are **implemented** in this
code base, followed by its **known limitations**. It describes no control
that does not exist.

## Implemented controls

### Authentication and sessions

- **Accounts.**
  - Internal users only: Administration and HR. Consultants never log in.
  - Users are created by an administrator with a temporary password and
    must change it before doing anything else.
  - The first administrator comes from a one-time, configuration-driven
    bootstrap. No credential is in source code or migrations.
- **Passwords:** minimum 12 characters, with upper case, lower case and a
  digit; stored by ASP.NET Core Identity's password hasher.
- **Lockout:** 5 failed attempts lock the account for 15 minutes. A failed
  login always returns the same generic message.
- **Cookies:** a single auth cookie, `HttpOnly`, `Secure`,
  `SameSite=Strict`, with an 8-hour sliding lifetime. No token is exposed
  to JavaScript.
- **Per-request validation:** every authenticated request re-checks that
  the user exists and is active, the security stamp, and a fingerprint of
  the role-permission map. There is no cached validation interval.
- **Session revocation:**
  - password change, role change and deactivation rotate the security
    stamp, which ends existing sessions;
  - logout revokes **all** of the user's sessions;
  - changing the permission map invalidates every older cookie.
- **Data Protection keys** (which encrypt the auth and CSRF cookies) are
  persisted to a configured directory under a fixed application name, so a
  redeploy neither logs users out nor weakens validation.

### Request integrity

- **CSRF:** a double-submit antiforgery token (cookie plus `X-CSRF-TOKEN`
  header) is required on every mutating endpoint, login included. It is
  re-issued after login.
- **Authorisation.**
  - Every controller action declares an explicit permission policy.
  - A fallback policy requires authentication for anything unannotated.
  - Permissions are claims derived from a single role-permission map.
- **Nested ownership:** destructive routes on nested resources (for example
  photo → inspection → item → Handover) verify the whole chain. A mismatch
  is a **404**, with no mutation, no file deletion and no audit row.
- **Mass assignment:** request contracts expose only editable fields.
  Lifecycle fields (status, asset tag, type) cannot be set by a client.
- **Concurrency:** lifecycle changes run in Serializable transactions with
  database constraints as backstop. Conflicts return **409**, never a
  partial write.

### Files

- Files live in **private storage** outside any web root and are never
  served statically. Authorised endpoints stream them after a permission and
  ownership check.
- **Upload validation.**
  - Images (JPEG, PNG, WebP) are checked by magic bytes, must match their
    declared type, and are limited to 10 MB.
  - Signed terms must be real PDFs (magic bytes), up to 15 MB.
  - Request-size limits apply per endpoint.
- **Path safety:** storage keys are random identifiers generated by the
  server. User-supplied file names are metadata only and never form a path.

### Spreadsheets

- **Imports:**
  - only `.xlsx` is accepted; macro-enabled files are rejected;
  - formula cells are rejected per field;
  - size, worksheet and row limits apply;
  - uploaded workbooks are never stored, and expired preview data is purged
    by a background worker.
- **Exports:** every user-controlled value is written as a text cell, and
  values starting with `=`, `+`, `-` or `@` are prefixed, so a cell can
  never become a formula (**formula-injection protection**).

### Email

- Plain-text bodies; MimeKit encodes headers (RFC 2047) and bodies
  (quoted-printable UTF-8).
- Addresses are parsed by MailKit. CR/LF is rejected in recipient
  overrides, which prevents header injection.
- TLS modes are explicit; `StartTls` never falls back to plaintext.
  Certificate validation is never disabled.
- A failed send logs one warning with the message type, delivery ID,
  failure category and correlation ID only: no recipient, body, credential
  or provider message.

### Audit and privacy

- Append-only audit log, readable by Administration only.
- Business changes and their audit row commit in the same transaction. A
  failed operation never writes a success row.
- **Audit privacy:** no passwords, cookies, tokens, security stamps or
  hashes are recorded. User updates record changed field names, not
  personal values.
- Every request has a correlation ID, returned in a response header and
  stored on audit rows.

### HTTP hardening

- **Rate limiting:**
  - global: 100 requests per minute per client IP;
  - login: a 10-per-minute fixed window.
- **API responses:** `X-Content-Type-Options: nosniff`, `Referrer-Policy`
  and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.
- **Outside Development:** HSTS and HTTPS redirection.
- **CORS:** an explicit origin list, never a wildcard with credentials.
- **Forwarded headers:**
  - trusted only from configured proxies; enabling them without naming a
    proxy stops startup;
  - the Docker package trusts only the reverse-proxy container, and Caddy
    discards forwarded headers sent by clients.
- **Errors:** generic ProblemDetails responses, never stack traces.
- **Frontend:** all user data is rendered as React text, with no raw-HTML
  rendering.

### Production configuration validation

When the environment is exactly `Production`, the API **refuses to start**,
listing every problem by setting name and never by value, if:

- the document issuer (legal name, address, tax ID) is missing or still a
  placeholder;
- the SMTP host, port, TLS mode or sender address is invalid;
- the sender display name or any signature line is missing or multi-line;
- `App:PublicBaseUrl` is not an absolute `https://` URL;
- the private-storage or key-ring path is missing, relative or not writable;
- the first-administrator bootstrap is enabled with example values: an
  `.invalid` email, or a `changeme` / `Replace-With` password.

It validates configuration only and never connects to SMTP at startup.

A demonstration client profile in Production logs a warning. No security
control is relaxed for it, and there is no demo bypass.

### Deployment and supply chain

- The API container runs as a non-root user from a runtime-only image with
  no source code, SDK or credentials.
- PostgreSQL is not published to the host network in the production package.
- **NuGet audit** is enabled and warnings are errors, so a restore fails on
  a known-vulnerable package. A vulnerable transitive dependency is pinned
  to a patched version where needed.
- CI runs `dotnet list package --vulnerable --include-transitive` and
  `npm audit`.

## Known limitations

These are accepted for the current scope and documented rather than hidden.

- **No multi-factor authentication.** Sign-in is email and password only.
- **No malware scanning** of uploaded files. They are validated by type and
  size only.
- **Image metadata is kept.** Uploaded photos are stored byte for byte,
  including EXIF metadata such as camera details and possibly GPS location.
  The upload screens ask users to photograph only the equipment.
- **No digital signatures.** Responsibility Terms are signed on paper or
  outside the application and uploaded as PDFs. The application records the
  SHA-256 of what it generates but does not validate cryptographic PDF
  signatures.
- **No independent penetration test** has been performed. The controls
  above are covered by automated tests.
- **The login rate limit is global**, not per client: a burst of login
  attempts can briefly delay other users' logins (per-account lockout still
  applies).
- **Single instance.** Rate limits are in memory. Running several API
  replicas is not supported.
- **The SPA has no Content-Security-Policy.** The reverse proxy sets HSTS,
  `nosniff`, `X-Frame-Options` and `Referrer-Policy`; the strict CSP covers
  API responses only.
- **Retirement-request notifications** are sent sequentially inside the
  request, which is slow with many administrators.
- **Consultant names may contain line breaks.** They appear only in
  plain-text email bodies, never in headers, but can display an extra line
  there.
- **Dates are UTC.** "Not in the future" checks use the UTC date, which
  can reject the local date shortly after midnight in time zones ahead of
  UTC.
- **Local filesystem storage only.** Backups of the storage volume, the
  database and the key ring are the operator's responsibility
  ([DEPLOYMENT.md](DEPLOYMENT.md)).
